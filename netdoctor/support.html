中文

它是干什么的？

菜单栏常驻的网络诊断工具。随时显示一个延迟数字，一键分层排查「到底断在哪一层」，并导出一份能直接发给别人的纯文本报告。只诊断，不修改——它不会改你的代理、DNS、路由或任何系统设置。

怎么用？

左键点菜单栏图标开面板，右键出菜单。面板有三个页签：诊断、历史、关于。按 Esc 关掉面板。菜单栏图标的位置会被记住，拖到哪下次就在哪。

菜单栏那个圆点和数字是什么？

圆点是当前状态，颜色就是「一眼看出通不通」。数字是延迟，等宽字体，每 10 秒更新一次。屏幕休眠时这个刷新会停掉，醒来立刻补一次。

五层分别是什么？
层它回答的问题
物理连接网卡拿到地址了吗？还是只有 169.254 这种「没拿到 DHCP」的地址？
局域网网关路由器和本机之间通不通？
DNS 解析域名能不能解析成地址？是你配的 DNS 服务器没答，还是它答了但答错了？
公网出口不经过 DNS、直连一个公网 IP，通不通？
关键节点我这边是通的，那是不是只有某个服务不通？
为什么叫「分层」？直接说通不通不就行了？

因为「网断了」这三个字对排查没有用。分层之后结论是具体的：断在网关说明是 Wi-Fi 或路由器的问题；DNS 层断但公网层通说明是 DNS 服务器的问题；只有关键节点不通而公网层是通的，说明问题不在你这边，是那个服务自己挂了。这三种情况的处理方式完全不同。

它会不会冤枉我的路由器？

不会，这是专门处理过的一条。中间路由器经常不回应或限速 ICMP，所以「网关不搭理我」不等于「网关坏了」。如果网关没回 ICMP，但公网直连是通的，那网关会被判为「通」并附一句说明。反过来不成立：「只有 DNS 通、公网直连不通」时不会因此改判网关。

同一条道理的另一个用法：丢包和延迟只有持续到目标才算数，所以它不测中间跳，只测两端。去掉这条推理，你会看到「断在网关」而实际是运营商的问题——那是这个工具最不能犯的错。

某一层显示「未检测」是什么意思？

意思是没测，不是断了。层与层之间会截断：物理层不通的话，后面四层就没有意义了，会标成「未检测」而不是「不通」。

这两件事必须分开——「没测」和「测出来是坏的」是完全不同的结论，混在一起会把人引向错误的排查方向。

ICMP 被屏蔽了怎么办？

网关那一层会改用 TCP 兜底：如果 ICMP 没回应，会再试几个常用端口。连接被拒绝（RST）同样证明主机是活的，所以「对方拒绝了我」也会被正确地判成「通」。

判定慢和快的分界线在哪？
层超过这个值算偏慢为什么是这个数
局域网网关30 毫秒再高说明 Wi-Fi 信号或交换机已经在拖后腿
DNS 解析300 毫秒再高，网页会明显「卡一下才开始加载」
公网出口200 毫秒再高，视频会议就会开始丢字

菜单栏那个数字的变色点比整层判定更严一点（150 和 400 毫秒），因为菜单栏是常驻的，颜色老在变会让人分心，所以要真的差了才变色。

报告能直接发给别人吗？

能，两种形式：

  • 完整报告：一份纯文本 .txt，由你在系统保存面板里选位置，几十行，给 IT 或运维看。
  • 状态卡：一段排版过的短文本，可以直接发在聊天里。

两种都是给人看的排版，不是给机器解析的日志。

历史里存了什么？

最近 50 次的轻量记录：时间、每一层的结论、关键耗时。不保存完整报告正文——一份报告几十行，50 条就是几百 KB，对常驻应用是负担。可以单条删除，也可以一次清空。

抬头那个徽章为什么有时候显示「未测」？

因为它只反映这个进程里跑过的诊断，不从历史里捞最近一条充当「当前状态」。历史里那条可能是三天前的，把过期结论当成现在的状态显示，比老实说「未测」糟得多。这不是 bug，是刻意的。

「未测」和「检测中」都不是测出来的结论，所以措辞上也不会写成「未知」——那会让人以为坏了。

历史页回答的是另一个问题：「上次什么时候出的问题」。它和抬头徽章是两套数据，不要混着看。

徽章下面那行小字是什么？

是结论的新鲜度（「刚刚测完」「5 分钟前测完」），不是诊断耗时。诊断耗时在结论卡里（「总用时 172ms」）。这两个数字长得像，但一个说的是「多久以前测的」，一个说的是「花了多久」。要发报告给别人时，别把这两个说反了。

它会不会改我的网络设置？

不会，而且这一条是结构性的，不是承诺：整个工程里不允许出现任何写系统网络配置的 API——没有代理开关、没有 DNS 切换、没有 hosts 编辑，连「顺手改一下」的入口都不存在。这条由一个脚本机械检查：在全部源文件里搜 23 个写入型 API，再反查所有系统网络配置调用是否都在 9 个只读接口的名单里。这个检查每次跑测试都会执行。

它联网吗？会不会把我的数据传走？

会联网，但方式很有限：对外只有三种动作，全部只读——DNS 查询、TCP 连接（发个 SYN 就关，应用层一个字节都不发）、ICMP 回声。它没有 HTTP 客户端，不下载任何网页，不上传任何东西，也没有我们的服务器。 探测不带账号、不带设备标识符、不带任何业务数据，所以「连了谁」不构成隐私问题。详细的目标清单和读取范围见隐私政策。

需要什么权限吗？

不需要任何系统权限，也不会弹出授权框。 沙盒授权一共只有两条：沙盒本身，和出站网络。不写文件（导出走系统的保存面板）、不读你的用户目录、不要完全磁盘访问、没有 App Group。ICMP 用的是非特权模式，不需要管理员权限，也不装任何后台服务。它不需要辅助功能，也不需要输入监控。

它占资源吗？

菜单栏应用常年不退出，所以占用是设计的一部分：10 秒一次 TCP 握手（每天几千个 SYN，CPU 占用测不出来），屏幕休眠时停跑，探测永远不在主线程，关键节点并发上限 4 个，历史有 50 条的硬上限。

支持哪些系统？

需要 macOS 13.0 或更高版本。它是菜单栏应用，不占 Dock 图标。

已知不足

以下几条是作者自己标注的，写在这里而不是藏起来：

  • 真实的断网场景没有人工过一遍。 这是最该补的一条：拔网线、关 Wi-Fi、路由器断电、只在信号差的地方待着——这几种情况下五层的结论是否都说得通，目前还没有人手工验过。现有的结论都来自网络正常时的几次真跑。 如果你正好遇到断网，用它跑一次然后把报告发出来，会非常有价值。
  • 右键菜单和 Esc 关面板没有做过自动化核对（那需要辅助功能授权，本 App 刻意不申请），只人工点过。
  • 长跑内存曲线没有观察过：菜单栏应用连着跑一周之后的表现，是这类应用的老问题，还没有数据。

App 的功能是完整的，没有半成品；上面说的是「没有被验证到的部分」，不是「没做完的部分」。

怎么反馈问题？

到 GitHub Issues 提交。如果方便，把导出的报告贴上来（它本来就是给人看的排版），并说明当时是 Wi-Fi 还是有线、有没有连 VPN。

English

What is it for

A network diagnostic tool that lives in the menu bar. It shows a latency figure at all times, works out which layer is broken in one action, and exports a plain-text report you can send to someone. It diagnoses and never modifies: it will not change your proxy, DNS, routes or any other system setting.

How do I use it

Left-click the menu bar icon to open the panel, right-click for the menu. The panel has three tabs: diagnosis, history and about. Escape closes it. The icon's position is remembered, so it stays where you put it.

What are the dot and the number in the menu bar

The dot is the current state, and its colour is how you tell at a glance whether things are working. The number is latency, in a monospaced face, updated every ten seconds. That refresh stops while the screen sleeps and catches up on wake.

What are the five layers
LayerThe question it answers
Physical linkDoes the interface have an address, or only a 169.254 address meaning DHCP never completed?
Local gatewayIs the router reachable from this machine?
DNS resolutionDoes the name resolve, and if not, was it that your DNS server did not answer, or that it answered wrongly?
Public internetConnecting directly to a public IP without DNS, does it work?
Key nodesMy side is fine, so is it just one particular service that is down?
Why layers? Why not just say whether it works

Because "the network is down" is useless for working out what to do. With layers the answer is specific: a break at the gateway means Wi-Fi or the router; a break at DNS while the public layer works means the DNS servers; only a key node failing while the public layer works means the problem is not on your side at all, and that service is down. Those three call for completely different responses.

Will it wrongly blame my router

No, and that case was handled deliberately. Intermediate routers often ignore or rate-limit ICMP, so "the gateway ignored me" is not the same as "the gateway is broken". If the gateway does not answer ICMP but the direct public connection works, the gateway is reported as healthy with an explanatory note. The reverse does not hold: if only DNS works and the direct public connection does not, that does not change the gateway's verdict.

The same principle applies elsewhere: packet loss and latency only count if they persist all the way to the target, so it does not probe intermediate hops, only the two ends. Drop that reasoning and you would see "broken at the gateway" when the fault is really with your provider, which is the worst mistake this tool could make.

What does "not tested" on a layer mean

It means not tested, not broken. Layers truncate: if the physical link is down, the four layers after it are meaningless and are marked "not tested" rather than "failed".

Those two must stay distinct. "Not tested" and "tested and broken" lead you to different places, and conflating them sends people down the wrong path.

What if ICMP is blocked

The gateway layer falls back to TCP: if ICMP gets no answer, it tries a few common ports. A refused connection (RST) also proves the host is alive, so "the other end rejected me" is still correctly reported as reachable.

Where is the line between slow and fine
LayerSlow aboveWhy that number
Local gateway30 msBeyond that, Wi-Fi signal or a switch is already dragging
DNS resolution300 msBeyond that, pages visibly stall before they start loading
Public internet200 msBeyond that, video calls start dropping syllables

The menu bar figure changes colour at stricter points (150 and 400 ms), because the menu bar is always visible and a colour that keeps flipping is a distraction: it should only change when things really changed.

Can I send the report to someone

Yes, in two forms:

  • The full report: a plain-text .txt file at a location you choose in a system save panel, a few dozen lines, intended for IT or operations.
  • A status card: a short formatted block of text you can paste straight into a chat.

Both are laid out for people to read, not as machine-parsed logs.

What does the history store

A lightweight record of the last 50 runs: timestamp, the verdict for each layer, and key timings. The full report text is not stored, because at a few dozen lines each, 50 of them would run to hundreds of kilobytes, which is a burden for something that never quits. Entries can be deleted individually or cleared at once.

Why does the badge sometimes say "not tested"

Because it reflects only the diagnostics run in this process and does not reach into history for the most recent one to present as "current state". That stored entry might be three days old, and showing a stale conclusion as the present state is far worse than honestly saying nothing has been tested. This is deliberate, not a bug.

Neither "not tested" nor "testing" is a measured conclusion, so the wording avoids "unknown" as well, which would suggest something is broken.

The history tab answers a different question: when did it last go wrong. It and the badge are two separate sets of data and should not be read as one.

What is the small line under the badge

It is the freshness of the conclusion ("just finished", "finished 5 minutes ago"), not how long the diagnostic took. The duration is in the result card ("total 172 ms"). The two numbers look alike, but one says how long ago and the other says how long it took. Before sending a report to someone, do not mix them up.

Will it change my network settings

No, and this is structural rather than a promise: no API that writes system network configuration is permitted anywhere in the project. There is no proxy switch, no DNS switcher, no hosts editor, and no "while I am here, let me just fix that" entry point. A script checks this mechanically, searching every source file for 23 write-type APIs and then verifying that every system network configuration call is one of nine read-only functions. That check runs on every test run.

Does it go online, and can my data leak

It does go online, in a very limited way: three outbound actions, all read-only, being a DNS query, a TCP connection (send a SYN and close, with not one byte at the application layer) and an ICMP echo. It has no HTTP client, downloads no pages, uploads nothing, and there is no server of ours. The probes carry no account, no device identifier and no application data, so who it connected to is not a privacy question. The full target list and everything it reads are in the Privacy Policy.

What permissions does it need

None, and it never shows a permission prompt. The sandbox declares exactly two things: the sandbox itself and outbound networking. It writes no files (export goes through a system save panel), does not touch your home folder, does not ask for Full Disk Access, and has no App Group. ICMP is unprivileged, so no administrator rights are needed and no background service is installed. It needs no Accessibility and no Input Monitoring.

Does it use many resources

A menu bar app never quits, so its footprint is part of the design: one TCP handshake every ten seconds (a few thousand SYNs a day, with no measurable CPU cost), stopped while the screen sleeps, probes never on the main thread, key-node concurrency capped at four, and a hard limit of 50 history records.

Which systems are supported

macOS 13.0 or later. It is a menu bar app with no Dock icon.

Known gaps

These are the author's own notes, listed here rather than hidden:

  • Real disconnection scenarios have not been walked through by hand. This is the most important gap: whether the five layers all reach sensible conclusions when you unplug the cable, switch off Wi-Fi, power down the router, or sit somewhere with a weak signal has not been verified manually. Every current conclusion comes from a handful of real runs on a working network. If you happen to be having connection trouble, running this and sending the report would be genuinely useful.
  • The right-click menu and closing the panel with Escape have no automated check, since that would need Accessibility permission, which this app deliberately does not request. They have only been clicked by hand.
  • No long-run memory curve has been observed. How a menu bar app behaves after a week of continuous running is the classic weak point for this kind of app, and there is no data yet.

The app is feature complete with nothing half-finished; the above describes what has not been verified, not what has not been built.

Reporting a problem

File an issue at GitHub Issues. If you can, paste the exported report (it is laid out for people anyway) and mention whether you were on Wi-Fi or Ethernet and whether a VPN was connected.
