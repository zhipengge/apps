文辑 · 隐私政策

中文

文辑没有服务器。稿件、图片、音视频都只写在这台电脑的沙盒容器里，没有账号，没有自建后端，不内嵌分析、追踪、崩溃上报或广告 SDK。它确实会联网，但只有三处，且每一处都不是把稿件发给我们——下面逐条写清楚。

它和网络的关系

文辑申请了「出站网络」这一条权限，因为文稿里可能已经有别人的图片。除此之外它不需要网络：断网也能写稿、保存、切换平台、复制适配稿。断网时看不到的只有远程图片（显示成空白），以及「打开后台」会打不开。

三处会碰到网络的地方：

动作连到哪发生什么
打开一篇含有远程图片的稿子 图片自己原本所在的站点 编辑器与右侧预览会按图片的原始地址去取，否则显示不出来。请求由系统的 WebKit 发出，只取那张图，不带你的正文，也不带文稿标题。
点「复制并打开后台」 对应平台的创作页 复制完成后，把平台地址交给系统默认浏览器打开。此后浏览器里发生的一切（登录、上传、平台自己的统计）由该平台和你的浏览器负责，文辑既不参与也拿不到结果。
在编辑器里点一个链接 链接指向的地方 交给系统打开（通常是浏览器）。地址就是文稿里写的那个，文辑不改写也不检查它去哪。

一个必须说清楚的点：如果文稿里的图片是网上的图，打开这篇稿就会向那个图的站点暴露你的 IP 地址，以及「这台机器取过这张图」。这和本站无关，但它是真实发生的网络行为，我们不写成「完全离线」。想避免的话，把图插成本地文件即可——本地图片不走网络。

另外，复制出去的 HTML 里，本地图片会被嵌成内联数据（data URI），而远程图片的地址会原样留着。所以粘到平台后台之后，是那边的编辑器去取这张图，不是文辑。

我们处理什么、放在哪

数据用途位置
文稿标题、正文 HTML、文稿列表 编辑与本地保存 沙盒容器内的 Application Support/WeEdit/Documents/<文稿 id>/article.json
你插入的图片 / 视频 / 音频 在文稿里显示；导出时嵌进 HTML；小红书和微博还会写入剪贴板 同一文稿目录下的 media/。插入时是复制进来的，不保留对原文件的引用
剪贴板（写） 你点「复制适配稿」时，写入适配后的 HTML、纯文本，小红书和微博还包括图片数据 系统剪贴板。只有你点按钮才会写
剪贴板（读） 你点「链接」时，取你刚才复制的那个网址，填进文稿 内存，用一次即弃
导出的 HTML 文件 你点「导出」时写出 你在保存面板里选的位置

文辑不使用偏好设置存储，因此没有额外的一份「使用痕迹」留在系统里；也没有安全作用域书签，所以它不会在你不用的文件上保持长期访问权——图片是拷进来的，拷完就和原文件无关了。

权限

文辑的沙盒授权只有三类，全部列在这里，没有别的：

  • App 沙盒——限定文稿只能写进自己的容器。
  • 你选定的文件（读与写）——插入图片/视频/音频、导出 HTML 时，通过系统的打开与保存面板拿文件。
  • 出站网络——只用于上面那三种情况。没有「接受入站连接」的授权，所以文辑在结构上无法作为服务器被连入。

不申请、也不需要：辅助功能、输入监控、完全磁盘访问、屏幕录制、通知、自动化控制其他 App、通讯录、日历、位置、麦克风、摄像头。文辑不是菜单栏常驻程序，是普通窗口程序，关掉最后一扇窗口就退出。

我们不做的

  • 不把文稿发到任何自建服务器——文辑没有服务器
  • 不登录你的公众号、小红书、知乎、微博账号，不代你发布
  • 不接入广告、分析、崩溃上报或任何第三方 SDK
  • 不读取通讯录、位置、麦克风、摄像头
  • 不生成设备标识符，不做跨 App 追踪，不向第三方出售或分享任何数据
  • 不要求注册、登录或绑定邮箱

第三方

文辑没有引入任何第三方库（工程里没有包管理器依赖），也没有内置任何第三方素材——图标是用代码和矢量绘制的。除系统框架外没有别人的代码在跑。

数据留存与删除

数据一直留在这台电脑上，直到你删掉。删除方法：退出文辑，从「应用程序」里删除它，再移除 ~/Library/Containers/com.gezhipeng0201.WeEdit（文稿就在这个容器里）。容器删掉即无残留，我们这边没有任何副本，因为没有可以存副本的地方。

加密与出境

文辑不自研加密，也不用加密做存储或同步。用到的加密只有系统在 HTTPS 里的标准实现（取远程图片、浏览器打开平台站点时）。对应的出口合规申报为「不使用非豁免加密」。

儿童

文辑不收集任何人的数据，自然也不收集儿童的数据。它没有账号体系，也没有可供提交信息的地方。

这份政策和代码的对应关系

上面每一条都不是照模板写的，是从工程里核对出来的：沙盒授权文件里只有那三项，所以「不申请辅助功能」是结构性的而不是承诺；全工程搜索不到任何偏好设置读写，所以「不额外留使用痕迹」成立；导出时的图片来源替换只认 weedit-media:// 与 file: 两种前缀，其余一律原样放行，所以「远程图地址会保留、并且会向原站取图」是这个实现的必然结果，而不是我们选择的说法。政策与实现不一致时，以工程为准。

English

WeEdit has no server. Drafts, images, video and audio are written to this computer's sandbox container only. No account, no backend, no analytics, tracking, crash reporting or ad SDK. It does go online, in exactly three places, and none of them sends your draft to us. Each is spelled out below.

How it relates to the network

WeEdit is granted outbound network access because a draft may already contain someone else's image. Nothing else needs the network: writing, saving, switching platforms and copying the adapted draft all work offline. What does not work offline is remote images (they show blank) and opening a platform editor.

ActionConnects toWhat happens
Opening a draft that contains remote images The site that image came from The editor and the preview pane fetch each image from its original address, or it cannot be shown. The request comes from the system WebView, asks for that image, and carries neither your text nor your title.
Pressing Copy and Open Editor That platform's compose page After copying, the platform's address is handed to your default browser. Everything after that (sign-in, upload, the platform's own analytics) belongs to that platform and your browser; WeEdit neither takes part nor receives the result.
Clicking a link inside the editor Wherever the link points Handed to the system to open, usually the browser. The address is the one written in the draft; WeEdit does not rewrite it or check where it goes.

One thing worth stating plainly: if an image in your draft lives on the web, opening that draft reveals your IP address to that image's host, along with the fact that this machine fetched it. That has nothing to do with us, but it is a real network event, so we do not describe the app as fully offline. Insert the image as a local file and no network is involved.

In the copied HTML, images stored locally are inlined as data URIs, while remote image addresses are left exactly as they are. So after you paste, it is the platform's own editor that fetches those images, not WeEdit.

What we process, and where

DataPurposeWhere
Draft title, body HTML, draft list Editing and local save Application Support/WeEdit/Documents/<draft id>/article.json inside the sandbox container
Images / video / audio you insert Shown in the draft; inlined on export; also written to the clipboard for Xiaohongshu and Weibo media/ in the same draft folder. The file is copied in; no reference to your original is kept
Clipboard (write) When you press Copy, the adapted HTML and plain text are written, plus image data for Xiaohongshu and Weibo The system clipboard, and only when you press the button
Clipboard (read) When you press Link, the URL you just copied is read and inserted into the draft In memory, used once
Exported HTML file Written when you press Export Wherever you choose in the save panel

WeEdit does not use preferences storage, so no extra record of use is left in the system, and it holds no security-scoped bookmarks: media is copied in, and once copied it has nothing to do with the original file.

Permissions

The sandbox grants exactly three things; there are no others:

  • App Sandbox, so drafts can only be written into the app's own container.
  • User-selected files (read and write), used through the system open and save panels when you insert media or export HTML.
  • Outbound network, used only for the three cases above. There is no incoming-connections entitlement, so WeEdit cannot be connected to as a server.

Not requested and not needed: Accessibility, Input Monitoring, Full Disk Access, Screen Recording, notifications, automation of other apps, Contacts, Calendar, Location, Microphone or Camera. WeEdit is an ordinary windowed app, not a menu bar agent, and it quits when you close its last window.

What we do not do

  • No upload of drafts to a server of ours, because there is no server of ours
  • No sign-in to your WeChat, Xiaohongshu, Zhihu or Weibo account, and no posting on your behalf
  • No ads, analytics, crash reporting or any third-party SDK
  • No Contacts, Location, Microphone or Camera
  • No device identifiers, no cross-app tracking, no selling or sharing of data
  • No sign-up, sign-in or email required

Third parties

WeEdit links no third-party libraries (the project has no package manager dependencies) and bundles no third-party assets; the icon is drawn in code and vectors. Apart from system frameworks, no one else's code runs here.

Retention and deletion

Everything stays on this computer until you delete it. Quit WeEdit, remove it from Applications, then remove ~/Library/Containers/com.gezhipeng0201.WeEdit, where the drafts live. Removing the container leaves nothing behind, and we hold no copy, because there is nowhere for us to hold one.

Encryption and export

WeEdit implements no encryption of its own and uses none for storage or sync. The only cryptography involved is the system's standard HTTPS, used when fetching remote images and when the browser opens a platform site. The matching export compliance declaration is that the app uses no non-exempt encryption.

Children

WeEdit collects no one's data, children's included. There is no account system and nowhere to submit information.

How this policy maps to the code

Nothing above was written from a template; each claim was checked against the project. The entitlements file contains exactly those three entries, which makes "no Accessibility" structural rather than a promise. A search across the whole project finds no preferences read or write, which is what makes "no extra usage record" true. The export-time source replacement only accepts the weedit-media:// and file: prefixes and passes everything else through untouched, which makes "remote addresses are kept and fetched from their own host" a consequence of the implementation rather than a phrasing choice. Where this policy and the implementation disagree, the implementation is what ships.
